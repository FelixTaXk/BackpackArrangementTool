## 一、引擎 / 求解（收益最高）

### E1. 收敛 worker 与 orchestrator 的能量标量（半一致性债）
**现状**：Worker 用 `ewScalarOf`（total + items + 1e-3·adj + 1e-4·area，manW/defW/dmg 只进 `ewBetterLex` 词典序）；orchestrator 却用 `engOrchScalar`（把 1e8·manW + 1e5·defW + 1e2·dmg + 10·adj 折进单个标量）。两处排序口径并不完全等价，回火/交换按后者、每个 worker 的 best 晋级按前者。且 `engine-orchestrator.js:205` 注释自称「与 Worker 侧 ewScalarOf 逐字一致」**属失实**。
**收益**：消除跨 worker 交换时对"谁更好"的判据漂移；为后续任何新软项（含本次 damage-bond、抱团键）提供单一权威口径。
**成本/风险**：中高——需决定谁是权威并把两处统一；改动触及确定性基线，**必须用真实清单跑回归**确认结果不劣化。
**建议**：单独一个小版本做，配一组真实背包基线对比前后 best。
**2026-09-10 状态**：已列入「双属性抱团」同批改造（抱团键需同时在两处同步），见 `进度说明.md` 十九节。

### E2. 求解结束后"伤害贴邻"再精化一轮
**现状**：damage-bond 是最后破平软项，只在 total/默认档位全等时起效；真实背包里 total 差异大时该偏好几乎不出手。
**可选增强**：若你希望"加成法宝贴伤害法宝"在**分数相近**而非"严格相等"时也倾向，可在 polish 段（`ewFinishPolish` 已有多端点精化）对已 complete 解做一轮"在不降 total 的前提下重排以增 damageBond"的局部精化。当前实现刻意最弱以免扰动真实分数，故这一步是让特性"更常见地生效"的保守杠杆。
**2026-09-10 状态**：**升级**——用户诉求已扩为「双属性抱团」，且实测（十六件真实清单）确认 `bonus=712.5` 已优化到位、纯结构问题。原「晋级闸门」根因（`ewBetterThanBest` 仅能量相等才看字典序）同时卡住抱团键，故 E2 与「修闸门」合并为该批改造的必需项。

### E2.5.（新增 2026-09-10）双属性抱团与交界不浪费
**需求**：同属性法宝抱团（最大化 `sameAdj`）；异属性交界由 `bonusKind === 'none'` 的无加成件承担（最小化 `crossWaste`）。
**现状**：完全缺失——`adj` 只数邻接总数不分属性；比较链无属性维度键；异属性相邻对 `total` 贡献恒为 0、引擎不区分承担者。
**已定方案**：能量引导 + 比较链新增独立键，键位插在「手动/默认优先级向量之后」且**不进 `totalScore`**；dmg 保留并排其后。**必须同批修** `ewBetterThanBest` 晋级闸门（否则新键不生效）与 E1 的 `engOrchScalar` 口径。
**前置**：离线测算可达改善空间（进行中），确认抱团键是否真会出手。

### E3. LNS/算子权重自整定可视
**现状**：6 个 ALNS 算子带段式权重（opWeights），但 UI 只显示 Top3 名称。算子好坏全凭经验初值。
**收益**：把各算子按真实背包的命中/接受率做成自整定，长期收敛更快、更稳。

### E4. 棋盘 / 空间扩展抽象
**现状**：W×H 双 Uint32 位板、CSR 邻接全部按 7×6 静态优化。若未来出现更大背包或非矩形解锁，需重新评估 L、邻接表容量与 active mask 语义。当前“格子已解锁”概念耦合较深。
**收益**：前瞻性；若产品只有一种背包则无需做。

## 二、数据 / 评分

### D1. extraRates（伤害/暴击/…）是否真正进入优化
**现状**：`bonusStats` 注册表只有 atk/def/hp 三维；伤害等 rate-only 项走 `extraRates`，`normalizeItemRecord` 只在注册表内并入 base（rv=0 不传播）。当前求解**并不优化"伤害输出最大化"**，只是把伤害当作法宝标记（causesDamage）做软邻接。
**决策点**：若产品目标是"输出队最优"，应把伤害加成/基础伤害真正纳入可优化维；若目标是"最大化面板总属性 + 把加成贴到伤害件"，现状已够。
**成本**：改动评分目标与展示口径，属 P0 级需求评审，勿在未定稿前改。
**2026-09-10 实测（重要）**：全库 **32 件 provider 中 20 件 `bonusRates` 为空**，其加成写在 `extraRates:{伤害:N}`，导致**这 20 件贡献恒为 0**（"提升相邻法宝伤害"型，如蕴金戒/炎脉髓/玄黄令）。用户确认玄黄令确为"提升相邻法宝伤害"。→ **D1 影响面比原先估计的大得多**（当前 5/8 的 provider 是哑弹），建议优先定稿。
**2026-09-10 定稿（见 `进度说明.md` 19.8）**：方案已明确，**不扩 `bonusStats`**（会污染 totalScore），改为**独立计分通道**：
- 伤害/汲取/暴击伤害/治疗效果/护盾值 **无基础值** → **按「命中次数」计分**，**不进 totalScore、前端不展示**，仅驱动求解排序；
- 触发守卫：**伤害**＝同属性 ∧ 对方 `causesDamage`（用户确认解 A）；**其余 4 类**＝仅需同属性相邻（同现有 self）；
- 未建模 92 件中 **85 件是 self 型**，收益由「同属性抱团」决定 → **与抱团键共享同一套统计**。
- 用户选定节奏：**先建模扩维、验证后再做抱团**。第 16 节旧「8 维 bonusStats」设计已撤销。

### D2. 星级（长老放大）与伤害口径复核
**现状**：红品质按星级放大基础属性（战斗加成百分比与基础 atk/def/hp 系不同机制）。请确认 DB 里 133 条“加成法宝自身也造成伤害”的标记与游戏一致（本次仅透传 xlsx 的「伤害」列，未做业务校核）。

### D3. 数据源单一可信源 + 自动校验
**现状**：DB 由 `convert-excel.mjs` 生成，但 xlsx 存于 `E:\背包排列工具\`，工作区靠手动复制。若数据变更频繁，建议脚本化“拉取 + 转换 + 差异报告 + 校验”一步到位，并把校验失败（如 ID 漂移、品质非法）做进 CI 或发布门槛。

## 三、工程 / 可维护性

### E5. 一次性清理收尾
- `convert-excel.mjs` 依赖外部 `xlsx`（此前放 `%TEMP%\xlsx-conv`）——把依赖版本/来源写进 README 或做成 `package.json` devDependency，避免环境漂移。
- `docs/进度说明.md` 含历史失实记录（8 维注册表等）虽已加“十七、收口”修正，历史段落仍会误导；建议后续把旧历史归档、保留一份“当前真实状态”单一文档。

### P1. 把纯逻辑层（score-shared/engine-encoding/engine-orchestrator/solver）抽成可单测 npm 模块
**现状**：test-harness 已能在 Node 里加载真实源，但依赖 vm + 手工 DOM 桩。若持续加引擎特性，建议把这些纯函数层正式拆包，引入 jest/vitest 做 CI 回归，锁定“worker 与 rescore 双实现一致”这类最易漂移的契约。

### P2. 双实现一致性“契约测试”
**风险点**：`ewPairDefW`(worker 独立重建) 与 CSR `adjDefW`、score-shared vector 三者是**三份手工保持一致的逻辑**。本次加 damage-bond 又新增了三处同类镜像。强烈建议加一组“同一输入下三口径输出一致”的测试，专防未来改一处漏另一处。

### P3. 清除 __ 遗留注释 / 隐藏开关
`window.__ENGINE_LNS_ON__`、`__ENGINE_TEMPERING_OFF__`、`__SCORE_SELFTEST__` 等调试开关仍留在生产代码；建议收敛到统一 debug 入口或按构建环境剥离。

## 四、体验 / UI

### U1. 结果面板可视化“伤害贴邻”
**现状**：文字提示已在 statusBox。可在摆放网格上给“造成伤害的法宝”与“贴着它的加成法宝”加高亮/连线，让玩家一眼看懂为何这样摆。
**收益**：直接把引擎的软偏好翻译成玩家可理解的反馈。

### U2. 求解中“实时最优解”网格预览
**现状**：实时行只刷文字状态。可在后台搜索时用节流在棋盘区预览当前 best 摆放，边跑边看优化轨迹。

### U3. 手动邻接优先级与“伤害贴同属性”的冲突提示
若玩家手动把某加成法宝定为最高优先级，却把它放到了异属性/非伤害件旁，当前不报任何提示。可在结果里对“本可贴到伤害件却未贴”的加成法宝给出可行动的提示，帮助玩家理解比较顺序。

### U4. 求解参数解释内联化
比较顺序、节点/时间上限、并行 Worker 这些概念目前集中在 hint 文案；新手易困惑。可把「搜索档位 / 并行 / 上限」收敛成一个可折叠的“高级/专家”面板，默认只留“求解”主按钮。
